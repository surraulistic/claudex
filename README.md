# claudex

Поручить работу другой сессии Claude Code, узнать её состояние и получить
результат там, откуда поручали. Плюс одна короткая сводка по сессиям вместо
шести ручных вызовов: проиндексированная история склеена с живым состоянием
Herdr.

## Установка

```bash
./install.sh
```

Собирает бинарь, кладёт его в `~/.local/bin` и линкует скилл в
`$CODEX_HOME/skills` (по умолчанию `~/.codex/skills`). Для сборки нужен `go`,
для работы — `herdr` и `cass` в `PATH`. Sqlite встроен, отдельного `sqlite3`
не требуется.

## Обиход

```bash
claudex send <адресат> "<сообщение>"   # дать работу или продолжить начатую
claudex task list                      # что ещё ждут
claudex task <id>                      # состояние одного поручения
claudex task log <id>                  # подробный ход работы
claudex session list                   # кому можно отправлять
claudex doctor                         # цела ли обвязка
claudex done [<id>] "<что вышло>"      # отчитаться о своей работе
claudex supervisor                     # фоновый наблюдатель
```

Прежние имена работают и останутся: `delegate` = `send`, `tasks` = `task list`,
`digest` = `task log`, `peers` = `session list`. Новых вызовов на них лучше не
заводить.

### Адресат распознаётся сам

Первый довод `send` разбирается по убыванию точности:

| что передали | что происходит |
|---|---|
| идентификатор разговора | отправка ему |
| идентификатор известного поручения | продолжение начатой работы |
| имя или метка панели herdr | поиск разговора, который она ведёт сейчас |

Подходит и то и другое — **отказ со списком толкований**, а не догадка: одно
отправит работнику, другое продолжит чужую работу.

Если у работника работа уже идёт, сообщение **продолжает её**, а не заводит
второе поручение. Раньше заводило, и у одного исполнителя накопилось 62
незакрытых. Несколько незакрытых — отказ; `--new` заводит отдельное осознанно.

Имя панели — удобство для человека и первичный поиск. Рабочий адрес —
идентификатор разговора: панель переживает смену агента, идентификатор нет.
`--panel` оставляет прежний транспорт для панели с не-Claude агентом или с
закрытым разговором.

### Ожидание — явное

`send` не занимает ход: отчёт придёт сообщением. `--wait` заставляет дождаться,
и нужен он редко.

## Жизненный цикл поручения

Состояние выводится из журнала — отдельного хранилища нет, второй источник
правды рассинхронизируется.

| состояние | что значит |
|---|---|
| `created` | текст цел, исполнитель отказался принять |
| `sent` | ушло исполнителю, отчёта нет |
| `needs_input` | задача упёрлась в вопрос |
| `done` / `failed` | задача отчиталась, и отчёт дошёл до отправителя |
| `undelivered` | **отчёт есть, но отправителя не достиг** |
| `lost` | исполнитель закончил и промолчал |
| `abandoned` | без движения дольше трёх суток |
| `working` / `progress` | пишет наблюдатель; без него не выводятся |

Ради `undelivered` всё и затевалось: для отправителя недоставленный отчёт
неотличим от молчания, и сворачивать его в `done` нельзя.

`abandoned` убирает из живого списка то, что уже не ждут: на живом журнале 85%
«ожидающих» оказались старше недели. Ничего не удаляется — `--all`,
`claudex task <id>` и дожим видят их по-прежнему.

## Кому возвращается результат

Отправителю — тому, кто запустил `send`. Адрес выбирается из окружения по
убыванию точности: тред Codex, разговор Claude Code, панель herdr. Отдельного
флага под каждого вызывающего нет: возврат результата — свойство поручения, а
не особенность Codex.

```bash
claudex send license "<задача>" --notify-thread "$CODEX_THREAD_ID"
claudex send license "<задача>" --notify-session <id разговора>
```

`CODEX_THREAD_ID` наследуется потомками, а Codex умеет запускать Claude Code; у
того переменная означает уже «дед по процессу», а не «мой ведущий». Поэтому при
`CLAUDECODE` унаследованный идентификатор адресом не считается.

### Приходит событие, а не отчёт

```
claudex: поручение 43bc6e11 — готово (исполнитель wE:p13)
миграции применены на dev и stage

Это событие, а не отчёт. Подробности читай сам:
  claudex task 43bc6e11
  claudex task log 43bc6e11
```

Полный отчёт в диалоге — это инструмент, говорящий там, где должен говорить
собеседник, и готовый пересказ, который координатор повторит своими словами.
Событие называет, что случилось, и отсылает к первоисточнику.

Событием будят того, кто умеет его отработать: тред Codex и разговор Claude
Code — они запускают команды. Уведомление herdr читает человек, и отправлять
ему «прочитай сам» значит перекладывать работу инструмента на него, поэтому
панель получает отчёт целиком. `--full-report` возвращает прежнее поведение
везде. Что выбрано — видно в `claudex task <id>` и `claudex doctor`.

### Чем доказывается адрес

| состояние треда Codex | доказательство | что делаем |
|---|---|---|
| `live` | есть `thread-writer-locks/<id>.lock` | кладём в очередь |
| `known` | замка нет, но тред помнит `session_index.jsonl` | **кладём в очередь** |
| `unknown` | не знает никто | отказ `thread_unknown` |

Закрытый тред очередь **принимает и читает** — потом, когда его откроют.
Проверено на живом треде; так это видит и человек, у которого при первом же
сообщении доезжает всё накопившееся. Два дня здесь стоял отказ с объяснением
«очередь он примет молча и не прочитает никогда» — предположение, записанное
как факт, из-за которого сотня отчётов осела в канале вытягивания.

Имя сессии адресом не считается: `codex queue` его принимает, но в указателе
три треда подряд зовутся «license service». Адрес обязан быть идентификатором,
иначе отказ `unconfirmed_binding`.

Панель, за которой журнал видел больше одного разговора, адресом не считается
вовсе — отказ `pane_hosts_several_conversations`. Измерено: Codex ведёт
несколько разговоров за одной панелью, herdr называет из них один, и отчёт
попадал в разговор, который о задаче не знал.

Куда и почему напишем прямо сейчас — read-only:

```bash
go run ./cmd/routecheck            # панели
go run ./cmd/routecheck --threads  # треды Codex
```

## Разговоры Claude Code

У каждой живой сессии есть входящий сокет и запись в реестре
`~/.claude/sessions/<pid>.json` — разговор, имя, каталог, занятость. Запись в
сокет построчным JSON — документированный интерфейс; `claudex session list`
показывает, кому можно писать.

Это снимает рассогласование, ради которого строилась защита
`executor_conversation_changed`: панель переживает смену агента, а разговор —
нет. Промахнуться разговором нельзя по устройству, адрес и есть разговор.

Сокет сам по себе принимает что угодно — пишущий в него не обязан быть
потомком принимающей сессии. Доставит ли Claude Code сообщение модели или
придержит его, решает **`crossSessionInbound`** в `~/.claude/settings.json`:

```json
{ "crossSessionInbound": "accept" }
```

Без этого ключа сообщение от стороннего процесса — а claudex как раз сторонний,
не порождён принимающей сессией — Claude Code **придержит до ручного
подтверждения**: `send` в разговор Claude Code уедет, но прочитан не будет,
пока кто-то не нажмёт «принять» в интерфейсе. `accept` снимает это
подтверждение для всех входящих; `refuse` глушит их вовсе. По умолчанию ключ
не задан — ставить его должен тот, кто настраивает claudex, вручную.

## Настройка

Без этого claudex работает, но хуже: `done` остаётся единственным способом
узнать, что поручение кончилось, а наблюдатель не запущен и ничего не дожимает
сам.

### Приём сообщений в разговор Claude Code

```json
{ "crossSessionInbound": "accept" }
```

В `~/.claude/settings.json`. Без этого ключа сообщения от claudex в разговор
Claude Code доставляются, но держатся на ручном подтверждении в интерфейсе —
`send --session <id>` вернёт успех, а прочитан текст не будет. Подробнее — в
разделе «Разговоры Claude Code» выше.

### Хук завершения в Claude Code

```bash
claudex hook install
```

Печатает блок для `~/.claude/settings.json`:

```json
"Stop": [
  { "hooks": [ { "type": "command",
                 "command": "/Users/you/.local/bin/claudex hook stop",
                 "async": true } ] }
]
```

Вписывается в существующий массив `Stop`, а не заменяет его целиком — если там
уже стоит что-то своё (у нас рядом живёт moshi-hook), дописывается рядом, не
вместо. После правки claudex, запущенные до неё, хук не подхватят: читается при
старте сессии.

### Наблюдатель — фоновый процесс, не хук

```bash
nohup claudex supervisor --interval 60 --silence-grace 20m --archive-after 30 \
  >>~/.claudex/supervisor.log 2>&1 &
```

Ничего не настраивается сам: не хук, не служба, не сервис. Запускается вручную
и переживает только сессию терминала, в которой запущен, — выключили машину или
убили процесс, он не поднимется сам. `claudex doctor` покажет честно: работает
или нет, по живому pid, а не по файлу состояния.

`--interval` почти не стоит менять: проход — это чтение закэшированного журнала,
0.07 с. `--silence-grace` важнее: срок, после которого молчание считается
завершением работы, должен быть больше реального промежутка между ходами —
иначе наблюдатель будит посреди работы. `--archive-after` выключен по умолчанию
намеренно: журнал — единственная память о прошлой работе, переносить его в
архив без явного согласия не должно ничего.

### Переменные окружения

Платформенные — выставляет не claudex, а среда, в которой он запущен:

| переменная | кто ставит | что определяет |
|---|---|---|
| `CODEX_THREAD_ID` | Codex | адрес возврата, когда запущен изнутри Codex |
| `CLAUDE_CODE_SESSION_ID` | Claude Code | адрес возврата, когда запущен изнутри Claude Code |
| `CLAUDE_CODE_MESSAGING_SOCKET` / `_TOKEN` | Claude Code | сокет текущей сессии для доставки в разговор |
| `CLAUDECODE` | Claude Code | отличает «я сам Claude Code» от унаследованного `CODEX_THREAD_ID` |
| `HERDR_PANE_ID` | herdr | какая панель вызвала claudex, если не тред и не разговор |
| `CLAUDE_CONFIG_DIR` | Claude Code | где искать реестр `~/.claude/sessions/<pid>.json` |
| `CODEX_HOME` | Codex | где искать `thread-writer-locks` и `session_index.jsonl` |

Свои, необязательные — переопределяют расположение по умолчанию:

| переменная | умолчание |
|---|---|
| `CLAUDEX_INDEX` | `~/.claudex/index.db` |
| `CLAUDEX_SEARCH` | `auto` (режим `find` без явного `--mode`) |
| `CLAUDEX_CASS_BIN` | `cass` в `PATH` |
| `CLAUDEX_CASS_DB` | путь к базе cass по умолчанию |
| `CLAUDEX_CODEX_BIN` | `codex` в `PATH` |

Задавать их на постоянной основе нет причины — все поля есть ровно затем,
чтобы переопределить что-то разово, не трогая остальных.

## Наблюдатель

```bash
claudex supervisor                       # фоном, обычным процессом
claudex supervisor status                # работает ли, что сделал
claudex supervisor stop
claudex supervisor --once                # один проход, для cron
nohup claudex supervisor --interval 60 --silence-grace 20m \
  >>~/.claudex/supervisor.log 2>&1 &
```

Отчёт бывает написан и не доставлен: разговор отправителя успел закрыться.
Текст цел и ждёт в канале вытягивания, но уходит только при следующем вызове
claudex — то есть когда кто-то и так что-то делает.

Наблюдатель — **обычный процесс, не языковая модель**, и **отчёта от себя не
пишет**: пересказ работы, сделанный не тем, кто её делал, — выдумка с
интонацией уверенности. Он замечает смену состояния и будит отправителя, а тот
читает `task` и `task log` сам.

Тишина заложена в устройство: не больше трёх отчётов за проход, предел на
проход целиком, отказавший адрес откладывается вдвое дальше прошлого раза до
получаса. Доставленное не уходит дважды — дедупликация живёт в журнале. Адрес,
молчащий дольше трёх суток, попыток больше не отнимает: отчёт виден в
`claudex undelivered` с пометкой `·`, но дожим его не трогает.

Живость наблюдателя проверяется по процессу, а не по файлу: файл переживает
убитый процесс, и `doctor`, поверив ему, сказал бы «под присмотром» там, где
присмотра нет.

`--archive-after 30` включает уборку журнала раз в сутки. Срок меряется днями:
меньше суток — отказ, потому что такой довод значит перепутанные единицы.

## Завершение работы

`claudex done` называет исход — готово, провал, частично, заблокировано. Это
оценка, и дать её может только тот, кто работал.

Помнить про команду модель обязана сама, а помнит в шести случаях из десяти: на
журнале в 424 поручения отчитались 256. Поэтому завершение ловится ещё и хуком
`Stop` самой Claude Code — платформа сообщает об окончании хода и отдаёт текст
последней реплики:

```bash
claudex hook install    # покажет, что добавить в ~/.claude/settings.json
```

Хук ничего не печатает и никого не будит: он записывает, что ход кончился.
Окончание хода завершением не является — ход кончается и посреди работы, и на
вопросе, — поэтому решает наблюдатель, по длительности молчания. Разбудив за
молчуна, он говорит ровно то, что видно: «закончило молча; последняя реплика:
…». Исход не называет — мы видели, что работа кончилась, но не знаем, чем.

Отметка ставится, только когда у сессии открыто **ровно одно** поручение: конец
хода не говорит, какое из нескольких закончилось, и пометить все значит
записать догадку.

## Чтение и поиск

```bash
claudex brief                             # все живые панели разом
claudex sessions                          # кто жив и у кого есть история
claudex wE:p13                            # полный дайджест одной панели
claudex search wE:p9 "MessageWhiz"        # поиск внутри одной сессии
claudex find "river миграция"             # поиск по всем транскриптам
claudex find "wallet currency" --days 14  # не старше двух недель
claudex entry <entry-id>                  # запись целиком, без обрезки
claudex context <entry-id> --before 4     # разговор вокруг записи
claudex watch <цель>                      # дождаться, пока панель освободится
```

`brief` и `sessions` по умолчанию дают строку на панель. Полный JSON — под
`--json`, и он в двадцать раз дороже по контексту: умолчание должно быть
дешёвым.

`brief` укладывает все панели в один процесс: хвосты читаются параллельно,
обращения к индексу идут разом. Семь отдельных дайджестов стоят впятеро дороже
той же картины. Хвост запрашивается не длиннее высоты панели — за этой границей
herdr восстанавливает прокрутку, и десять панелей вместо 3 мс стоят секунду.

`find` ходит по всем транскриптам, включая давно закрытые сессии, и сворачивает
попадания в сессии: у каждой проект, каталог, ветка, число хитов и окно
активности. Ключ `target` у группы можно сразу передать в `claudex <target>`.
Слова объединяются через AND, хвостовая `*` даёт префикс, `--raw` пропускает
синтаксис FTS5 как есть.

`watch` блокируется, пока панель занята, и завершается, когда она освободилась.
Модель при этом не работает и токены не тратятся: ожидание живёт внутри herdr.
Запускать фоном. Код выхода 5 — не дождался; JSON при этом не печатается вовсе,
и состояние панели остаётся неизвестным, а не `idle`.

`entry` и `context` читают индекс напрямую и ничего не обрезают.

## Не для обихода

```bash
claudex tell <разговор> "<текст>"   # сырое сообщение без учёта
claudex flush                       # починка: дослать зависшее
claudex reconcile                   # починка: собрать за молчуна
claudex undelivered                 # что не дошло
claudex archive [дней]              # унести давнее в архив
claudex hook stop                   # служебное, зовётся хуком Claude Code
```

`tell` кладёт текст в разговор и **ничего не учитывает**: по нему нет
поручения, некому отчитаться и нечего восстанавливать, если он пропадёт. Ждёте
результат или продолжаете начатое — это `send`.

`flush` и `reconcile` — ручная починка; то же делает наблюдатель сам.

`reconcile` отчёта **не пишет**. Экран панели — свидетельство чего-то, но не
доказательство, что задача закончила именно этим: за всё время собранных с
экрана «отчётов» было два, и оба оказались мусором — обрывок таблицы и
переписка человека с соседней сессией. Увиденное уходит доказательством в
событие, отчётом не становится.

## Когда история отстаёт

Индекс собирается из базы `cass`, а она читает транскрипты своим ходом
(`cass index --watch --watch-interval 60`). Наблюдалось отставание в час при
живой работе. Выдача всегда несёт `freshness`: отставание индекса, свежесть
самой базы и причину, если данные неполны. Пустая история при живой панели —
это «индекс отстал», а не «сессия молчала».

## Коды выхода

`0` успех, в том числе с деградировавшей историей · `2` цель не найдена или
неоднозначна · `3` Herdr недоступен · `4` ошибка вызова · `5` не дождался ·
`6` панель занята, задание не отправлено · `7` сбой herdr при ожидании — исход
неизвестен. Читать `7` как `5` нельзя: «не смогли узнать» — не «не завершилось».

## Скрипты

```
tools/delegate-and-monitor.zsh   обёртка над send с логом и расшифровкой кода
tools/herdr-guard.zsh            необязательный перехват прямых herdr agent prompt
```

`herdr-guard.zsh` по умолчанию **не установлен**. Он отклоняет прямой
`herdr agent prompt` — тот отправляет задачу, но никто не ждёт её завершения, в
журнале пусто, и привязать наблюдателя задним числом нельзя. Панель со статусом
`working` и `watched: false` в `sessions` — это и есть след прямого вызова.

Проверяются поведение и договорённости, а не строки. Каждое правило, которое
дорого ошибиться, покрыто мутационным зондом: правка, ломающая смысл, обязана
ронять тест — иначе тест проверяет пересказ, а не код.
