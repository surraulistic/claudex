# Ревью claudex, 11.09.2026

Исследовательское ревью Go-версии: чистота и скорость. Ветка `review/cleanup`,
одиннадцать коммитов с правками плюс этот отчёт; `make test` зелёный на каждом. Всё измерено на рабочей
машине и рабочих данных: индекс 3753 разговора / 256 363 записи / 672 МБ,
живой herdr с десятью панелями.

Порог запуска процесса — 8.2 мс (медиана `claudex tasks`; минимум `claudex help`
— 7.3 мс). Его стоит вычитать из всех чисел ниже: это пол, ниже которого
команда не бывает.

---

## I. Ошибки в поведении

Это не стиль. Каждая проверена на собранной команде, ни одна не исправлена —
исправление каждой меняет форму выдачи или код выхода, а это ваше решение.

### 1. `claudex <цель>` отдаёт текст вместо JSON — единственная команда, не попавшая в сверку

README («Что на выходе») и `SKILL.md` («Reading a digest — Compact JSON
(`--pretty` for humans) in four parts») описывают дайджест одной панели как
JSON с `target`, `alias`, `live`, `history`, `tail`, `signals`.

На деле:

```
$ claudex install
wE:p13  claude  idle  license

  … строки хвоста …

разговор 1568 · claude_code · записей 3481
  [258384] assistant Значения у меня нет — я его намеренно не держал…
```

`cmd/claudex/main.go:cmdDigest` печатает `fmt.Printf`, а не `emit`. Отсюда:

- нет `target`, `alias`, `label`, `kind`, `pane_id`, `session_id`, `focused`;
- нет `context_pct` и `limits` — ровно тех полей, по которым `SKILL.md` велит
  решать, можно ли давать панели новую задачу («A pane near 100% context is
  about to compact: let it finish, do not hand it a new task»);
- нет `signals` вовсе;
- нет `watched`, нет `history.reason`, нет `chars`/`truncated` у записей;
- `--pretty` игнорируется (проверено: вывод байт в байт тот же).

Прежняя версия это отдавала. `git show 6765a81^:lib/digest.js`, функция
`buildDigest`, собирает ровно документированную форму, включая ветку закрытой
сессии (`live: null`, история из индекса) — то, что `SKILL.md` описывает как
способ читать закрытую сессию.

Почему пропустили: в спеке `2026-09-11-claudex-go-design.md`, раздел «Полная
сверка выдачи», перечислены двенадцать вызовов — `sessions`, `brief`, `find`
(три), `entry` (два), `context` (два), `search` (два), `sessions --cwd`.
Дайджеста одной панели в этом списке нет. Единственная команда, которую не
сверяли, — единственная, которая разошлась.

Это самая дорогая находка ревью: `SKILL.md` — договор, по которому чужие
агенты читают чужие сессии, и по нему они ждут JSON.

### 2. `delegate --no-wait` пишет в панель, ждущую решения человека

`cmd/claudex/main.go:cmdDelegate`, ветка `o.noWait`, проверяет только
`a.Status == "working"`. `blocked` и `unknown` проходят.

Доказательство (поддельный herdr на настоящем сокете, живых панелей не
касался) — `blocked`-панель, один и тот же вызов с флагом и без:

```
delegate … --no-wait     код 0  ОТПРАВЛЕНО: проверочный текст
delegate … --timeout 2   код 6  панель занята: wE:p9 в состоянии "blocked"
```

Это ровно тот случай, который в спеке описан как оплаченный ошибкой: «`blocked`
значит, что панель ждёт решения человека, и произвольный текст уедет **ответом
на этот вопрос**». `task.freeStates` заводили именно из-за него — а вторая
дверь осталась открытой. `--force` на этой ветке тоже не читается: он там не
нужен, потому что отказа нет.

Попутно: `--no-wait` ничего не пишет в журнал поручений. `SKILL.md` обещает
«`claudex tasks` prints that journal: every send, every report, every outcome»,
и в `sessions` такая панель не получит `watched: true`.

Правка — одна строка, но она меняет код выхода с 0 на 6:

```go
if !freeStates[a.Status] && !o.force {
    return exitcode.Errorf(exitcode.Busy, "панель занята: %s в состоянии %q", p.ID, a.Status)
}
```

(`freeStates` придётся вынести из `internal/task` в экспортируемое место или
завести проверку там же.)

### 3. `delegate` никогда не возвращает код 7

Договор: «`7` сбой herdr при ожидании — исход неизвестен. Читать `7` как `5`
нельзя: „не смогли узнать“ — не „не завершилось“». `cmdWatch` различает их по
`herdr.CodeOf(err) == "timeout"`. `cmdDelegate` — нет: любая ошибка
`agent.prompt` становится исходом `не уложилась в срок` и кодом 5.

Проверено на поддельном herdr:

```
herdr сломался во время ожидания (internal_error)   код 5
herdr не дождался (timeout)                         код 5
```

`exitcode.Unknown` во всей программе используется ровно в одном месте — в
`cmdWatch`.

### 4. Ошибка вызова даёт код 1, а не 4

Договор во всех трёх местах (usage, README, SKILL) обещает `4 ошибка вызова`.
На деле:

```
claudex sessions --arm        код 1   (flag provided but not defined)
claudex search wE:p13         код 1   (нужны цель и запрос)
claudex entry                 код 1   (нужен номер записи)
claudex entry абв             код 1   (strconv.ParseInt)
claudex delegate wE:p13       код 1   (нужны цель и задача)
```

Код 4 возвращается только из четырёх мест внутри `delegate`. То есть самый
частый способ ошибиться в вызове выдаёт «общий сбой».

### 5. `--detach` теряет `--force`

`cmd/claudex/main.go:detach` собирает доводы дочернего процесса руками:
`{"delegate", pane, prompt, "--timeout", o.timeoutRaw}` плюс `--notify`.
`--force` и `--db-path` не передаются. То есть
`claudex delegate X "…" --detach --force` вернёт `detached: true`, а
отсоединённый наблюдатель откажется отправлять кодом 6 — в свой лог, которого
никто не читает.

## II. Что применено

Одиннадцать коммитов. У каждого измерение или падающий тест.

### 1. Поиск: отбор по разговору и сроку до ранжирования (`c76c25e`) — ошибка

`store.Search` брал у FTS5 окно `limit*4` лучших по рангу **по всему индексу**
и только потом отсеивал чужой разговор и старые записи.

```
claudex search 846a1bcf-… wallet              было 0 результатов
  (в этой сессии 421 попадание на «wallet»)
claudex search 846a1bcf-… wallet --limit 20   было 2
claudex find wallet --days 1                  было 1 попадание, есть 8
```

Отбор перенесён в тот же запрос, что и `match`. Внутреннее окно было не
защитой по скорости, а ошибкой: без него в запросе меньше работы.

| запрос | было | стало |
|---|---|---|
| `find wallet` | 28.1 мс | 27.1 мс |
| `find wallet --days 14` | 28.4 мс | 24.6 мс |
| `search 1647 wallet` | 29.0 мс | 19.4 мс |

Два регрессионных теста; оба падают на прежнем запросе, оба зелёные на новом.
Выдача `find` без фильтров не изменилась: сверено на девяти запросах живого
индекса с `--limit 3/8/20`.

### 2. Окно вокруг записи без нумерации всей беседы (`b732cda`)

`context` считал `row_number()` по всем записям разговора ради тридцати строк.

| разговор | было | стало |
|---|---|---|
| 2020 (11 681 запись) | 30.2 мс | 7.5 мс |
| 1647 (10 348) | 26.9 мс | 6.2 мс |
| 3199 (6 552) | 17.0 мс | 4.1 мс |

Сверка: 2400 случаев (400 случайных якорей × шесть форм окна, включая нулевое
и заведомо шире беседы) — расхождений нет. Плюс 300 сверок готовых команд.

### 3. `resolve`: один `agent.list` вместо двух (`240c362`)

`livePanes()` и `tabLabels()` каждый сам ходил за списком агентов. Посчитано
прокси-сокетом перед herdr:

```
claudex install                 agent.list=2 → 1
claudex search install wallet   agent.list=2 → 1
```

`agent.list` — самый дорогой вызов herdr (тёплый 2–5 мс; по спеке изредка
замирает на 110–120 мс), второй раз он ничего не добавлял.

### 4. Дайджест панели: два запроса — по индексу (`cd84c1e`)

Замер по частям показал, что почти всё время дайджеста — форма двух запросов,
а не объём данных.

- **Поиск разговора по цели.** Три «или» в одном запросе, из них `like '%…'` и
  `cast(id as text)`: `EXPLAIN QUERY PLAN` → `SCAN conv`. 1.5–2.1 мс на каждую
  панель, независимо от размера беседы. Точный `session_id` теперь спрашивается
  отдельно и идёт `SEARCH conv USING COVERING INDEX conv_session`: **0.01 мс**.
  Остальные два ключа — тем же запросом и в том же порядке.
- **Последняя активность.** Индекс `msg` начинается с `(conv_id, is_tool)`, и
  шорткат sqlite для `max()` включается, только когда `is_tool` закреплён.
  Значений два, поэтому максимум берётся по обеим группам: на беседе в 11 748
  записей **1.45 → 0.02 мс**.

### 5. `--detach` и гонка вокруг pid (`260c363`)

- `~/.claudex` не заводился перед открытием `detached.log`. До первого
  `claudex index` или первого поручения `--detach` падал кодом 1 с текстом
  `open …/.claudex/detached.log: no such file or directory`. На пустом HOME:
  было 200 падений из 200, стало ноль.
- `go cmd.Process.Release()` шёл параллельно с чтением `cmd.Process.Pid`.
  На unix `Release` пишет `Pid = -1` без синхронизации. Под `-race`
  воспроизводится сразу (`WARNING: DATA RACE`, печатается `pid: -1`); на живом
  коде за 200 запусков не сработала ни разу — скрытая гонка, а не
  наблюдавшаяся ошибка. Так и записано в коммите.
- `herdr.Agents/Tabs/Get/Prompt/Wait` возвращали `out.Поле, c.Call(…, &out)`.
  Порядок вычисления операнда и вызова в одном `return` спецификация Go не
  задаёт; работает это лишь потому, что gc вычисляет вызовы первыми (проверено
  отдельной программой на go1.26.1). Ошибка отсюда была бы тихой: пустой список
  агентов при `nil`-ошибке.

### 6. Чистота (`c3c13b5`, `fc392f2`, `c2736d0`, `4c439ed`, `70bc0cf`, `6b2d653`)

- **`trim` и `trimTo`** в `main.go` — мёртвые (проверено
  `golang.org/x/tools/cmd/deadcode` по точке входа). `trim` вдобавок повторял
  `textual.Clip`, но резал на знак короче.
- **`textual.Cut`** собирал две регулярки на каждый вызов, тогда как все
  остальные регулярки пакета лежат на уровне файла. 20 000 итераций × 6:
  **7.07 → 5.27 мкс/вызов**. На команде это тонет в шуме — правка ради того,
  чтобы в файле был один способ заводить регулярку.
- **`cmdSessions`** держал виды, сырые экраны и записи истории в трёх слайсах,
  а порядок вывода — в четвёртом, перестановке индексов. Отсюда
  `less(views)(order[a], order[b])`: замыкание, пересобираемое на каждое
  сравнение. Теперь всё про панель — одна запись, сортируется она сама,
  `less` берёт два вида. Три ветки «пустая строка → nil» в `toBrief` и две в
  сборке вида сведены к `orNull` (был цикл по анонимной структуре с `**string`).
- **`splitArgs`**: ветка про `=` делала то же, что код под ней.
  **`state.Reconcile`**: запись в карту стояла в обеих ветках развилки.
  **`index.refresh`**: какие аргументы подставлять, решалось поиском `?` в
  тексте запроса. **`store.Digest`**: выбирал `source_path`, который никто не
  читает. **`cmd/probe`**: мерил `session.info`, которого в herdr нет, и каждый
  раз печатал простыню «unknown variant» вместо замера.
- **`exitcode`** объявлен договором о кодах выхода, а держал разбор срока
  ожидания: `parseTimeout` переехал в `main.go` вместе с тестом. Оттуда же убран
  код 8 (`NotArmed`) — отдельной фазы взведения в Go-версии нет, код не
  возвращается ниоткуда и в usage/README его нет.
- **README** обещал три вещи, которых в команде нет: флаг `--arm`
  (`flag provided but not defined`), поле `unindexed_mb` (нет в выдаче) и
  `final_status: unknown` при коде 5 (JSON при таймауте не печатается вовсе —
  проверено на поддельном herdr). `SKILL.md` описывает это верно.

## III. Что намеренно не применено

### `textual.Clip` остался без единого вызывающего

Единственным был `trimTo`. Удалять не стал: вы назвали его держащим вес, и
отличие от `Cut` (не схлопывает переводы строк) настоящее. Но правило, ради
которого он заводился, сегодня держит не он — `cmdContext` отдаёт `e.Text` как
есть, вообще не обрезая. Решение за вами.

### Половина `internal/state`, весь `internal/watch` и подписки `herdr` не достижимы из бинаря

`deadcode` по `cmd/claudex`: `State.Apply`, `State.Reconcile`, `State.Get`,
`Pane.differs`, `Client.Subscribe`, `parseEvent`, `Sub.params`, `StatusSubs`,
`Subscription.*`, `Event.Text`. Это машинерия демона (`claudexd` в спеке
помечен как необязательный), она покрыта тестами и работает — но сегодня CLI
ходит в herdr по одному запросу на вызов и событий не слушает. Ничего не
трогал: revision-фильтр, игнорирование `agent_status` из `pane_updated` и
сверка `Reconcile` — ровно то, что вы просили не трогать не разобравшись.
Отмечаю как факт: около 400 строк (`watch.go` 163, подписки в `herdr.go` ~143,
`State.Apply` и `State.Reconcile` ~93) живут для демона, которого пока нет.

### Догон индекса: `conv` переписывается целиком

Профиль `claudex index` (догон, ничего нового):

```
attach                10.4 мс
conv                  28–32 мс   ← 3753 строки переписываются каждый раз
msg                    1.7 мс
msg_fts                6.0 мс
meta                   0.1 мс
```

Отфильтровать неизменившиеся можно — CTE с именованной «свежей» выборкой и
сравнением строкой значений (`is not` по кортежу). Измерено: **28–32 → 12–22 мс**.
Не применял: SQL вырастает с пяти строк до семнадцати ради 12 мс на команде,
которая идёт раз в день и целиком стоит 64 мс. Обмен плохой. Если захотите —
форма проверена и лежит в этом абзаце.

Отдельно: полезные колонки `conv` (`agent`, `session_id`, `source_path`,
`workspace`) после создания разговора не меняются, а `title`, `started_at`,
`ended_at` не читает вообще никто. Значит теоретически можно вставлять только
новые разговоры — но это уже смена поведения, и молчаливая.

### Порядок вывода, форма JSON, коды выхода

Не трогал ничего из этого. Единственное расхождение во всей сверке (47 вызовов
`find`/`entry`/`context` плюс `sessions`, `brief`, `sessions --cwd`, дайджест
панели, дайджест по id разговора без `session_id`, дайджест по хвосту имени
файла Codex, код выхода и текст на несуществующей цели) — это
`find wallet --days 1`: было 1 попадание, стало 8. Ради этого правка и сделана.

## IV. Чего доказать не удалось

### Обрыв на `--source recent`: видел, не воспроизвёл

В первом же замере по панелям обнаружилось, что `recent` на покоящейся панели
дорожает скачком между 24 и 28 строками:

```
панель     статус     4     8    12    16    20    24    28    32    40    44
w1:p2      done     0.6   0.6   0.5   0.5   0.6   0.6 184.5 197.9 220.6 239.3
wE:pB      idle     0.3   0.3   0.3   0.3   0.3   0.3 372.6 380.0 378.6 330.9
wE:p13     idle     0.4   0.5   0.3   0.3   0.3   0.5 184.9 219.9 203.3 226.7
wE:p1A     idle     0.3   0.3   0.3   0.5   0.4   0.5  40.9  51.5  43.0  42.9
wQ:p1      idle     0.2   0.2   0.2   0.2   0.3   0.3 379.7 381.2 380.0 379.6
```

Минимум из пяти прогонов на каждую клетку, то есть дорого было все пять раз.
`rawTail` просит `min(lines*4, herdr.CheapLines)` — для `sessions` это 40, для
`brief` 32, обе величины за обрывом. `claudex sessions` в тот момент стоил
**421 мс** (лучшее из семи), из них 380 мс — ожидание самой медленной панели.

`CheapLines = 40` откалиброван по `visible` и по высоте панели (44 строки). У
`recent` граница другая и ниже.

**Но воспроизвести не смог.** Через несколько минут все панели отдавали
`recent` по 0.3 мс на любом числе строк вплоть до 64, и `sessions` вернулся к
28 мс. Сбор 200 парных замеров (24 против 40, порядок чередуется, каждые 15 с
в течение получаса) дал: максимум для 24 строк — 9.2 мс, для 40 строк —
110.6 мс, и таких случаев два. 110 мс — это ровно те «заминки herdr», которые
описаны в спеке (пять вызовов из тридцати, 116–122 мс), а не обрыв на границе.
Два случая из двухсот — намёк, не доказательство.

Отдельно проверил на своей панели: первое чтение после свежего вывода изредка
стоит ~108 мс **на любом источнике и любом числе строк** (`visible` при n=12,
`recent` при n=24) — то есть та же заминка, к границе экрана отношения не
имеющая.

Почему ничего не менял. Опустить потолок для `recent` до 24 небезопасно:
на панели `wR:p1` чтение 24 строк давало **ноль** строк после `CleanTail`, а 40
строк — двенадцать. Это изменение выдачи. Безопасная форма — «прочитать дёшево,
доплатить только если строк не набралось» — стоит лишней ветки и лишнего
чтения, а обоснование под ней сейчас держится на двух замерах из двухсот.

Если состояние вернётся, ловить его так:
`go run ./cmd/probe` не поможет — он мерит только `visible`. Нужен парный замер
`recent` на 24 и на 40 строк по всем покоящимся панелям.

### Стоимость `find` на частом слове

`find wallet` — 36.5 мс, из них 27 мс сам запрос FTS5. 8042 попадания,
`order by rank` считает bm25 по всем. Обойти это, не меняя ранжирование, я
способа не нашёл; окно `limit*4`, которое выглядело как оптимизация, ею не было
(см. I.1 — оно было ошибкой). Это пол, а не провал.

## VI. Как проверялось

- **Паритет выдачи.** Скрипт гоняет обе сборки на одних доводах и сравнивает
  JSON с отсортированными ключами: 47 вызовов `find` (девять запросов ×
  `--limit 3/8/20`, `--days 1/7/14/90`), `entry` и `context` на четырёх записях
  × четыре формы окна; плюс `sessions`, `brief`, `sessions --cwd`, дайджест
  панели, дайджест закрытой сессии по id разговора и по хвосту имени файла
  Codex, код выхода и текст на несуществующей цели.
- **Окно `context`.** 2400 сверок запроса против запроса на случайных якорях и
  300 сверок готовых команд.
- **Вызовы herdr.** Прокси-сокет перед настоящим herdr считает методы.
- **Ошибки и коды выхода.** Поддельный herdr на настоящем unix-сокете:
  `blocked`-панель, отказ `agent.wait` с кодом `timeout`, отказ `agent.prompt`
  с `internal_error`, пустой HOME. Живых панелей не касался, никому ничего не
  делегировал.
- **Мёртвый код.** `golang.org/x/tools/cmd/deadcode` по точке входа
  `cmd/claudex` (пересобран под go1.26.1 — установленный бинарь был собран
  go1.25 и отказывался читать модуль).
- **Каждый коммит** прогнан отдельно: `go vet ./... && go test -race ./...` —
  одиннадцать из одиннадцати зелёные.
